## Product design

### Goals / Non-goals

**Goals (v1):**
- An MSPbots tenant can connect its own Grafana instance (Cloud or self-hosted) to the Agent Platform by entering a base URL and a Grafana Service Account token — no MSPbots-side changes needed per tenant.
- Once connected, an agent can: search/browse dashboards and folders, inspect a dashboard's panel layout, list and inspect datasources, run a query against a datasource (the actual "live access to current data" capability), list alerting rules and contact points, search existing annotations, and create a new annotation (e.g. to record that an agent took an action).
- Every tool fails loudly and specifically (structured error, not a silent empty result or a hang) when the token is missing/invalid, the instance is unreachable, or the token's role is insufficient for a write.

**Non-goals (v1):**
- No dashboard/folder/datasource/alert-rule create, update, or delete. Read-first; the one write tool is annotation creation, which is additive and scoped to a single resource (never bulk, never destructive).
- No user/team/org administration (`/api/users`, `/api/teams`, `/api/org`) — not part of "live access to Grafana" as the agent's job here, and it widens the blast radius of the Service Account unnecessarily.
- No OAuth connect flow. Grafana Service Account tokens are the vendor's own recommended non-interactive credential; building an OAuth app registration flow is out of scope for v1 and not required by the ticket.
- No Grafana Cloud–specific telemetry endpoints (Cloud "Access Policies" / direct Prometheus-remote-read access) — those are a different auth model Grafana documents separately from the standard HTTP API (`https://grafana.com/docs/grafana/latest/administration/service-accounts/`); the connector only needs the standard Grafana HTTP API, which works the same way for Cloud orgs and self-hosted instances once a Service Account token exists.
- One connector instance == one Grafana org (whichever org the Service Account belongs to), same scoping convention every other credential-style MSPbots connector uses.

### Acceptance criteria AC1..AC11

- AC1: Given a Grafana Service Account token (role Viewer or higher) and the instance's base URL, When a tenant adds the Grafana connector in MSPbots Agent Platform (Capabilities → Connectors → Grafana) with those two fields, Then the connection succeeds and an agent can immediately list dashboards from that instance.
- AC2: Given a connected Grafana connector, When an agent asks what dashboards exist matching a search term (optionally scoped to a tag or a folder), Then the agent receives a list of matching dashboard titles, uids, and folder names, capped at the tool's page size.
- AC3: Given a connected Grafana connector, When an agent asks to inspect one dashboard's panel layout, Then the agent receives the dashboard's title, tags, folder, and the list of its panels (id, title, type, datasource) — not the full raw dashboard JSON, unless the raw form is explicitly requested.
- AC4: Given a connected Grafana connector and a configured backend datasource (e.g. Prometheus) with a known uid, When an agent runs a query against it over a time range, Then the agent receives the result frames returned by Grafana's query engine for that datasource.
- AC5: Given a connected Grafana connector, When an agent lists alert rules (optionally scoped to a folder), Then the agent receives each rule's title, folder, no-data/exec-error state configuration, and whether it is paused.
- AC6: Given a connected Grafana connector with an Editor-or-higher-role token, When an agent creates an annotation on a dashboard with specific text, tags, and time, Then the annotation appears on that dashboard in Grafana with the given text, tags, and timestamp.
- AC7: Given a missing or invalid Service Account token, When any tool is called, Then the agent receives a structured `unauthorized` error, not a silent empty result and not an unhandled exception.
- AC8: Given a Viewer-role token, When an agent calls the create-annotation tool, Then Grafana's own permission rejection is surfaced as a structured `unauthorized` error and no annotation is created.
- AC9: Given a wrong or unreachable base URL, When any tool is called, Then the agent receives a structured `upstream_error` within the tool's bounded timeout/retry budget — not a hang and not a bare 500.
- AC10: Given two different MSPbots tenants each with their own Grafana connector (different base URL + token), When tenant A's agent calls a tool concurrently with tenant B's agent, Then neither tenant's credentials nor data ever appear in the other tenant's response.
- AC11: Given a dashboard whose JSON representation is larger than the tool's per-call size budget, When an agent fetches it, Then the tool returns the compact summary form rather than failing or silently truncating mid-JSON.

## Tech design

### Conclusion

Build `grafana-mcp` as a new Python/FastMCP service under `MSPbotsAIFramework/grafana-mcp`, same shape as every other credential-style MSPbots vendor-mcp repo (`itglue-mcp`, `sentinelone-mcp`, etc.): Streamable HTTP, stateless, credentials from two request headers (`X-Grafana-Base-Url`, `X-Grafana-Token`), one `httpx.AsyncClient` per request built from those headers. 12 tools wrapping Grafana's documented legacy `/api/*` HTTP API (not the newer namespaced `/apis/*.grafana.app/v1` surface — see Option analysis). This is a from-scratch build (main-line A); the repo currently has no code.

### Where the current implementation lives

- `MSPbotsAIFramework/grafana-mcp@main (2eec5ea)`: `README.md` only, no source tree. Nothing to extend.
- Adjacent same-shape implementation used as the template for layout and conventions: `MSPbotsAIFramework/itglue-mcp@main (abf9dd7)` — `src/itglue_mcp/{__init__.py, __main__.py, server.py, config.py, credentials.py, api.py, tools/{__init__.py, _common.py, <domain>.py...}}`, `pyproject.toml` deps `mcp>=1.10.0,<2.0.0`, `httpx>=0.27.0`, `pydantic-settings>=2.3.0`, `uvicorn>=0.30.0`, `starlette>=0.41.0`; error envelope built in `api.py:50-57` via `_json.error(code, message, retryable, status)` with codes `invalid_argument`/`rate_limited`/`upstream_error` mapped from upstream HTTP status; `tests/test_tools.py` + `tests/test_middleware.py` pattern. `grafana-mcp` should copy this layout and dependency set rather than invent a new one (SKILL.md A3/A5, "reuse first, build second").

### Option analysis

| Decision point | Option | Pros | Cost | Chosen |
|---|---|---|---|---|
| Stack | FastMCP (`mcp` pkg) + httpx + pydantic-settings + starlette/uvicorn, same as every existing vendor-mcp repo | zero new tooling, matches org convention, every SOP requirement (`stateless_http=True`, DNS-rebinding off, lifespan mounting) already solved once | none found | **Yes** |
| Grafana API surface | Legacy `/api/*` (search, dashboards, datasources, ds/query, annotations, provisioning) | documented as not-being-disabled; identical behavior across self-hosted (any recent version) and Cloud; this is what every third-party Grafana integration targets today | will eventually need a follow-up once Grafana fully retires the legacy surface (no announced date) | **Yes** |
| Grafana API surface (rejected) | Newer namespaced `/apis/dashboard.grafana.app/v1`, `/apis/folder.grafana.app/v1` | forward-looking, resource-oriented | only confirmed present on recent Grafana versions (App Platform-based dashboards/folders); MSP customers run a wide, uncontrolled spread of self-hosted versions — targeting this surface risks `404`s against older instances that have no fallback in v1 | No — revisit once we have real tenant version data |
| `get_dashboard` return shape | Compact summary (title/uid/tags/folder/panels list) by default, `include_raw` flag for full JSON | keeps responses inside the token-economy budget (SOP A4, ≤20000 chars/call); dashboards can carry hundreds of panels with full query definitions | summary loses some detail an agent might want; mitigated by the raw-JSON escape hatch | **Yes** |
| Alert-rule folder filter | Client-side filter (tool fetches `GET /api/v1/provisioning/alert-rules`, filters by `folderUID` in code) | Grafana's provisioning API has no folder query param | one extra round trip cost is already paid by the fetch | **Yes — no alternative; endpoint has no server-side filter** |
| Auth model | Grafana Service Account Bearer token | Grafana's own recommended non-interactive credential (`https://grafana.com/docs/grafana/latest/administration/service-accounts/`), revocable, scoped by role (Viewer/Editor/Admin) | requires the Grafana admin to create a service account instead of reusing a personal login | **Yes** |
| Auth model (rejected) | HTTP Basic (username/password) | simpler for a very old self-hosted instance that has no Service Account support (pre-v8.5) | ties the connector to a real human/admin password, harder to scope/rotate, Grafana itself steers users toward Service Accounts | No — service accounts cover the overwhelming majority of instances MSPs actually run today |

### Data & API contract

Request headers (both required on every call; validated by `credentials.py`):

| Header | Required | Meaning |
|---|---|---|
| `X-Grafana-Base-Url` | Yes | Base URL of the target Grafana instance, e.g. `https://acme.grafana.net` or `https://grafana.internal.example.com`. Must be `https://` (or `http://` for an explicitly-internal self-hosted instance — accepted, not blocked, since many self-hosted MSP instances sit behind a private network without TLS). |
| `X-Grafana-Token` | Yes (masked) | Grafana Service Account token (`glsa_...`), sent upstream as `Authorization: Bearer <token>`. Created in Grafana under **Administration → Service accounts** (role Viewer for v1's read tools; Editor or higher if the tenant also wants `grafana_create_annotation` to work). |

Tools (12), each: MCP tool name → upstream Grafana call → MCP-side shape. Upstream paths and example payloads sourced from `https://grafana.com/docs/grafana/latest/developers/http_api/{folder_dashboard_search,dashboard,data_source,annotations,alerting_provisioning,other}/` and `.../administration/service-accounts/` (fetched 2026-11-02):

1. `grafana_search_dashboards(query?, tag?, folder_uid?, limit?)` → `GET /api/search?type=dash-db&query=&tag=&folderUIDs=&limit=` → `{"items": [{"uid","title","url","tags","folderUid","folderTitle"}...], "has_more": bool}`.
2. `grafana_get_dashboard(uid, include_raw?)` → `GET /api/dashboards/uid/:uid` → default: `{"uid","title","tags","folderUid","panels":[{"id","title","type","datasource"}...]}`; `include_raw=true` returns the full upstream JSON, still subject to the 20000-char truncation rule (`truncated: true` + `has_more`-style marker if cut).
3. `grafana_list_folders(limit?)` → `GET /api/search?type=dash-folder&limit=` → `{"items":[{"uid","title"}...], "has_more": bool}`.
4. `grafana_list_datasources()` → `GET /api/datasources` → `{"items":[{"uid","name","type","url","isDefault"}...]}` (field list trimmed from Grafana's full datasource object, which includes secrets fields that are never forwarded).
5. `grafana_get_datasource(uid)` → `GET /api/datasources/uid/:uid` → same trimmed shape, single object. Secret fields (`secureJsonFields`, `basicAuthPassword`, etc.) are dropped before returning — the agent gets connectivity metadata, never upstream datasource credentials.
6. `grafana_query_datasource(datasource_uid, query, from?, to?, max_data_points?)` → `POST /api/ds/query` with body `{"queries":[{"refId":"A","datasource":{"uid":...},"maxDataPoints":...,...<query>}],"from":"now-5m","to":"now"}` → `{"results": {"A": {"frames": [...]}}}` passed through (already compact; Grafana's own frame format).
7. `grafana_list_alert_rules(folder_uid?, limit?)` → `GET /api/v1/provisioning/alert-rules`, filtered client-side on `folderUID` → `{"items":[{"uid","title","folderUID","ruleGroup","noDataState","execErrState","isPaused"}...], "has_more": bool}`.
8. `grafana_get_alert_rule(uid)` → `GET /api/v1/provisioning/alert-rules/:uid` → same trimmed shape, single object, plus `"condition"`.
9. `grafana_list_contact_points(limit?)` → `GET /api/v1/provisioning/contact-points` → `{"items":[{"uid","name","type"}...]}` (notification target `settings` — which can carry secrets like webhook URLs/SMTP creds — is dropped).
10. `grafana_search_annotations(from?, to?, tags?, dashboard_uid?, limit?)` → `GET /api/annotations?from=&to=&tags=&dashboardUID=&limit=` → `{"items":[{"id","dashboardUID","panelId","time","text","tags"}...], "has_more": bool}`.
11. `grafana_create_annotation(text, tags?, dashboard_uid?, panel_id?, time?, time_end?)` → `POST /api/annotations` body `{"text","tags","dashboardUID","panelId","time","timeEnd"}` → `{"id": <int>}`. `destructiveHint=false`, `idempotentHint=false` (Grafana does not dedupe — repeated calls create duplicate annotations; documented in the tool description so an agent does not blindly retry on an ambiguous failure).
12. `grafana_get_health()` → `GET /api/health` (no auth header required by Grafana itself, but the tool still requires `X-Grafana-Base-Url` since it needs to know which instance to ask) → `{"version","database"}` (drops `commit`, which is an internal build hash with no agent-facing value).

Error envelope (shared across all 12 tools, same shape as `itglue-mcp`): `{"error": {"code", "message", "retryable"}}`, `code` ∈ `not_configured | unauthorized | not_found | invalid_argument | rate_limited | upstream_error`. Mapping: Grafana `401` → `unauthorized`; `403` → `unauthorized` (insufficient Service Account role); `404` → `not_found`; `400` → `invalid_argument`; `429` → `rate_limited`, `retryable=true`; `5xx`/timeout/connection error → `upstream_error`, `retryable=true`; missing/malformed headers → `not_configured`/`invalid_argument` before any upstream call is made.

Backward compatibility: not applicable — first version, no existing tenants, no prior tool contract to preserve.

### Key flow / sequence

```
Agent → MCP Gateway (adds X-Grafana-Base-Url, X-Grafana-Token from the tenant's stored connector config)
      → grafana-mcp /mcp (Streamable HTTP)
          → credentials.py: read + validate headers, set ContextVar
          → tools/<domain>.py: build request from ContextVar + tool args
          → api.py: httpx call to <base_url>/api/... with Authorization: Bearer <token>
          → Grafana instance
          ← JSON response (or error)
      ← api.py maps status → envelope (success passthrough / {"error": {...}})
      → tools/<domain>.py: trims to the compact shape, applies limit/truncation
      → credentials.py: reset ContextVar in `finally`
← MCP Gateway logs the call (tool name, status, duration — not headers, not response body) and returns to the agent
```

### Non-functional

- **Idempotency/concurrency**: all 11 read tools are naturally idempotent (safe to retry). `grafana_create_annotation` is not — Grafana assigns a new `id` on every call; the tool description tells the agent not to retry on an ambiguous outcome (e.g. a timeout after the request was already sent), only on a clean `upstream_error`/`rate_limited` that never reached Grafana.
- **Performance**: per-call outbound timeout 5s connect / 30s read (SOP §5 default); bounded retry+backoff on `429`/`5xx`, total time per tool call < 120s; one `httpx.AsyncClient` constructed per request from the header-derived base URL (no shared/global client — a shared client would otherwise point at whichever tenant connected first).
- **Security**: credentials read only from `X-Grafana-Base-Url`/`X-Grafana-Token`, never written to disk/env/logs; any `Authorization` value Grafana might echo back in an error body is stripped before the envelope leaves the service; no datasource/contact-point secret fields are ever forwarded to the agent (tools 4/5/9 above).
- **Multi-tenant isolation**: per-request `contextvars.ContextVar` holding `(base_url, token)`, set on request start and `reset()` in a `finally` block — same pattern as `itglue-mcp`; no module-level or global Grafana client/cache, so two tenants' concurrent requests on the same running container never share state (AC10).
- **Observability**: structured log line per tool call (tool name, upstream status, duration, truncated/has_more flags) — never the header values, never the raw Grafana response body (dashboard/panel content can be customer-sensitive). Health/readiness via `GET /health` (local only).

### Rollout & rollback

- New vendor, no existing tenant connections — first deployment goes through `/api/vendor-register` (not `/api/deploy-int`, since the gateway does not know this vendor yet), registering `name: grafana`, `display_name: Grafana`, `credential_fields: {"X-Grafana-Base-Url": {...}, "X-Grafana-Token": {type: "password", ...}}`.
- No feature flag / gradual rollout needed — a brand-new connector only starts mattering once a tenant explicitly connects it; there is no existing traffic to protect.
- Rollback: nothing to roll back to (no prior version). If a defect is found post-registration, the fix ships as a normal `dev/<ticket>` → merge → `/api/deploy-int` update; registration itself is not repeated.

### Risks & dependencies

- **Risk**: Grafana version drift across MSP tenants' self-hosted instances — some very old instance might not support Service Account tokens (pre-v8.5) or might have a legacy endpoint quirk. Mitigated by targeting the documented-stable legacy `/api` surface and by every tool surfacing Grafana's own status/body as `upstream_error` on failure (visible, not silent) rather than assuming success.
- **Risk**: dashboards can be very large (hundreds of panels, full query JSON per panel) and exceed the per-call token budget — mitigated by the compact-summary default (AC11, Option analysis).
- **Risk**: a tenant creates the Service Account with Admin role (broader than needed) — the connector itself still only ever calls the 12 documented endpoints regardless of the token's granted role, so this does not expand what the agent can actually do; documented in the README to recommend Viewer (or Editor only if annotation-writing is wanted).
- **Dependency**: none on any other open PRD ticket. Depends only on the existing MCP gateway `/api/vendor-register` / `/api/deploy-int` infrastructure already used by every other connector — no new platform capability required.

### Decisions made by DEV01

- **Auth header design**: `X-Grafana-Base-Url` + `X-Grafana-Token` (Service Account Bearer), not Basic auth. Why: Grafana's own documented recommendation, revocable and role-scoped, consistent with how every other credential-style MSPbots connector is shaped. Alternative: HTTP Basic (username/password) — rejected, ties the connector to a real admin login instead of a revocable scoped token.
- **API surface**: legacy `/api/*` Grafana HTTP API, not the newer namespaced `/apis/dashboard.grafana.app/v1` / `/apis/folder.grafana.app/v1`. Why: documented as not being disabled and known to work across the full version spread MSP tenants run; the namespaced surface is confirmed only on recent Grafana versions. Alternative: build against the namespaced surface — rejected for v1, flagged as a follow-up once real tenant version data exists.
- **`get_dashboard` default shape**: compact summary, not full raw JSON. Why: token economy (SOP A4) — full dashboard JSON can be very large. Alternative: always return raw JSON — rejected, would blow the per-call size budget on real-world dashboards; `include_raw` flag kept as an escape hatch.
- **Write surface**: exactly one write tool (`grafana_create_annotation`), explicitly resource-scoped (never bulk, never destructive). Why: "live access" does not imply dashboard/alert management, and SOP A4 defaults every tool to read-only unless there is a clear business reason for a write. Alternative: also expose dashboard/alert CRUD — rejected, no requirement asked for it and it meaningfully widens the blast radius of a leaked/misused token.
- **Alert-rule folder filtering**: done client-side after fetching the full list. Why: Grafana's provisioning API has no server-side folder filter; there is no alternative that avoids the extra round trip.
- **List pagination caps**: `limit` default ≤50, hard cap ≤200, deliberately below Grafana's own defaults (e.g. `/api/search` defaults to up to 1000). Why: SOP A4 token-economy rule; agents rarely need more than a page at a time, and an uncapped Grafana-side default would blow the response budget on any customer with a large dashboard count.

### A documented deviation from the SOP's generic pattern: no HTTP 401 for a missing credential header

The SOP's general guidance (§3.2) is that a missing required header makes `/mcp` return HTTP `401`. This connector does **not** do that: `CredentialMiddleware` never blocks the request — `initialize` and `tools/list` always return `200` regardless of headers (same rationale as the itglue-mcp `PRD-20835` fix: the platform's admin console refreshes a connector's tool catalog with placeholder/absent headers). A missing or malformed credential is instead reported as the **same in-band JSON error envelope** every other tool error uses (`not_configured` / `invalid_argument`), applied inside `tools/_common.py:run()` before any outbound call.

This is a deliberate technical decision, not an oversight: the design's own test case **TC7** requires exactly this — `grafana_search_dashboards()` called with the token absent must return `{"error": {"code": "not_configured", ...}}` with **zero outbound calls**, not an HTTP-level rejection with a different body shape. An HTTP 401 response is a different JSON shape (`{"error": "...", "required_headers": [...]}` in the itglue pattern) and would also mean `tools/list` could not succeed without headers, which TC7's own setup (and the admin-console precedent) rules out. Per `legs/dev.md` S2, technical design is dev's freedom as long as it doesn't change the AC's user-visible behavior; from the agent's point of view, "receiving a structured error indicating missing credentials, before any upstream call" (SOP §3.2's intent) holds either way. Flagging this explicitly for the review leg since it's a literal deviation from the SOP checklist line "a missing header makes `/mcp` return 401" — happy to revisit if review disagrees, since this is the one section where I knowingly chose the test case's literal shape over the SOP's example implementation.

### Other technical choices worth flagging

- **Time-range parameter names**: `grafana_query_datasource`/`grafana_search_annotations` use `time_from`/`time_to` instead of `from`/`to` (the names used loosely in the design prose) because `from` is a Python reserved word. Values and defaults (`"now-5m"`/`"now"`) are passed straight through to Grafana's `/api/ds/query` and `/api/annotations`, which both accept Grafana's relative-time strings natively — no client-side time parsing was added.
- **`grafana_get_health` does not require a token** (`run(..., require_token=False)`): Grafana's own `/api/health` needs no auth; the tool still requires `X-Grafana-Base-Url` so it knows which instance to probe. This matches the tech design's explicit note on this tool.
- **No Grafana-specific SDK dependency added**: only the already-standard vendor-mcp stack (`mcp`, `httpx`, `pydantic-settings`, `uvicorn`, `starlette`) per the tech design's Reuse & cleanup section — the HTTP surface used is small enough that a thin `httpx` wrapper (copied in shape from `itglue-mcp`) was simpler than adopting a third-party Grafana client, and keeps the implementation clean-room (SOP rule 3).
