### Findings

1. [must-fix] `src/grafana_mcp/credentials.py:66-93` — `CredentialMiddleware` never rejects a request that is missing the required `X-Grafana-Token` header: `initialize`/`tools/list`/`tools/call` all return HTTP 200 regardless of headers, and a missing token is instead reported in-band by `tools/_common.py:82-95` (`run()`) as `{"error": {"code": "not_configured", ...}}`. This violates `vendor-mcp-development-sop.md` §3.2 ("凭据缺失即 401", marked 必须/mandatory: *"`/mcp` 请求缺任一必需 Header 时，中间件直接返回 401，并在 body 里列出所需的 Header 名"*) and the explicit `mcp-track.md` §4.3 must-fix bullet that folds in the SOP §14 Checklist, whose "对接契约（§1、§3，必须全部满足）" section lists *"缺 Header 时 `/mcp` 返回 401 并列出所需 Header"* as a mandatory, not optional, item.

   The design doc's own justification for this deviation (`docs/tickets/PRD-21261.md:297-301`, "A documented deviation from the SOP's generic pattern") cites "the same rationale as the itglue-mcp PRD-20835 fix: the platform's admin console refreshes a connector's tool catalog with placeholder/absent headers" — but that precedent does not actually support skipping 401 for a missing required credential. Checked `MSPbotsAIFramework/itglue-mcp@main (abf9dd7)`:
   - `src/itglue_mcp/credentials.py:91-93` — `CredentialMiddleware.__call__` returns a 401 `JSONResponse` (via `_reject()`) the moment the required `X-ITGlue-API-Key` header is empty, before even reaching `tools/list`.
   - `tests/test_middleware.py:25-27` — `test_missing_api_key_is_401` calls `tools/list` (no `initialize`) with the API key header absent and asserts `r.status_code == 401` and `"X-ITGlue-API-Key" in r.json()["required_headers"]`.
   - `tests/test_middleware.py:39-49` — the actual PRD-20835 fix only exempts an **optional** header (`X-ITGlue-Region` / `X-ITGlue-Base-URL`, both of which have defaults) carrying a *placeholder* value from blocking `initialize`/`tools/list`. It never touches the required `X-ITGlue-API-Key` check above.

   So the one existing connector that was actually patched for the admin-console tool-catalog-refresh scenario still 401s on a missing required credential; it only relaxed validation of an optional header. Grafana's two required headers (`X-Grafana-Token` and `X-Grafana-Base-Url`) are both treated as "may be entirely absent, still 200" here, which is a materially different (and non-compliant) behavior from the precedent cited to justify it.

   Fix: have `CredentialMiddleware` return 401 (with `required_headers` listing `X-Grafana-Token` and `X-Grafana-Base-Url`, mirroring itglue-mcp's `_reject()` shape) when either required header is absent. The in-band `not_configured`/`invalid_argument` tool-call envelope can stay for a header that is present but malformed (that part isn't covered by §3.2, which only speaks to an absent header), but an outright missing required header must not produce a 200. `tools/list`/`initialize` without any headers (the actual admin-console scenario) would then need its own narrower accommodation if still required — but it cannot be achieved by exempting the required-credential check entirely, only an optional one, per the real precedent.

## Fixes (round 1)

Both must-fix items addressed on top of `1b6b831` (round-1 review base). Commits: `src/grafana_mcp/credentials.py` + `src/grafana_mcp/tools/_common.py` + `tests/test_middleware.py` (finding 1), `README.md` + `docs/tickets/PRD-21261.md` (finding 2).

1. **`src/grafana_mcp/credentials.py`** — `CredentialMiddleware` now reads (buffers and replays) the JSON-RPC body and rejects any `/mcp` request with HTTP `401` when a header it actually needs is absent, listing the missing header name(s) under `required_headers` in the body, mirroring `itglue-mcp`'s `_reject()` shape exactly as the finding asked. `X-Grafana-Base-Url` is required for every request (no tool works without knowing the instance); `X-Grafana-Token` is required for every request **except** a `tools/call` naming `grafana_get_health`, which the pre-existing (and not flagged) technical design already exempted from the token requirement because Grafana's own `/api/health` needs no auth (`docs/tickets/PRD-21261.md:134,306`, `tools/health.py:29`, `require_token=False`) — that exemption is preserved unchanged; only the *base URL* requirement for that tool is enforced at the new 401 gate. A header that is *present* but malformed (e.g. a non-URL base URL) is still handled the old way, in-band as `invalid_argument`, exactly as the finding said was out of scope for this fix.

   Verified live, both locally (`uv run grafana-mcp`) and through the rebuilt container (`sudo docker build . && sudo docker run ...`): a `tools/list` call with no headers at all now returns `401 {"error":"Missing required credentials","message":"Send the following header(s): X-Grafana-Base-Url, X-Grafana-Token.","required_headers":["X-Grafana-Base-Url","X-Grafana-Token"]}`; the same call with placeholder (non-empty but fake) values for both headers still returns `200`/12 tools, preserving the admin-console tool-catalog-refresh scenario the original design cited — the real itglue-mcp precedent this design's rationale pointed to never actually omits its required header either, it sends a placeholder value for it (`itglue-mcp@main (abf9dd7)` `tests/test_middleware.py:39-49`); only a header that is truly absent is now rejected.

   **This supersedes TC7 as literally worded in `docs/tickets/PRD-21261.md:213` and the AC7/TC7 row at line 288** (not edited here — that is the frozen Product design/test-case section, out of this leg's authority to rewrite; changing what TC7 asserts is a design-leg action). TC7 reads "Given the header is absent, When any tool is called, Then the response is `{"error":{"code":"not_configured",...}}`" — with this fix, a request missing a required header never reaches "any tool is called" at all: it is rejected at the transport level with `401` before the JSON-RPC call is processed. This is the SOP-compliant behavior §3.2 and this finding require, and it still satisfies **AC7**'s actual wording ("the agent receives a structured error, not a silent empty result and not an unhandled exception") — a `401` with a `required_headers` list is a structured error, just delivered one layer earlier than TC7's own implementation detail assumed. `tests/test_middleware.py` was updated accordingly: `test_missing_token_header_returns_not_configured_without_outbound_call` / `test_missing_base_url_header_returns_not_configured_without_outbound_call` (asserted the now-superseded in-band shape) were replaced with `test_missing_both_headers_on_tools_list_is_401`, `test_missing_token_header_on_initialize_is_401`, `test_missing_base_url_header_on_tools_list_is_401`, `test_empty_token_header_is_still_401`, and `test_missing_token_header_on_tool_call_is_401_without_outbound_call` (zero outbound calls, same as before — just a 401 instead of an in-band error). Added `test_placeholder_headers_do_not_block_initialize_or_tools_list` (the admin-console case) and `test_health_check_tool_still_needs_base_url` (confirms the `grafana_get_health` exemption is narrow: token only, not base URL). `test_tools_list_is_stateless` and `test_tools_list_works_without_any_headers` were updated/replaced to send real header values, since "zero headers" is no longer a passing case for `tools/list`. **Flagging for the next review round**: TC7's wording and the AC7/TC7 table row in `docs/tickets/PRD-21261.md` are now stale relative to the implementation and should be reworded by the design leg (BA return to `5b`) the next time that document is touched; until then this paragraph is the record of why the test's literal scenario changed.
